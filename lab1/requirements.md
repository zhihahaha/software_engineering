# 酒店预订系统 - 软件需求文档

## 需求列表

### REQ-001 用户角色与权限控制

- 类型：功能需求
- 来源：INT-01-L004, INT-02-L019, INT-02-L020
- 优先级：高
- 状态：已确认
- 需求描述：系统支持三类用户角色：顾客、酒店工作人员、平台管理员。酒店工作人员只能管理自己所属酒店的信息和订单，不能修改其他酒店的信息或处理其他酒店的订单。平台管理员可以管理平台上的所有酒店。
- 前置条件：用户已注册并登录系统
- 正常结果：系统根据用户角色展示对应功能权限；顾客可查询酒店和预订房间，酒店工作人员可管理自己酒店的信息和订单，平台管理员可管理平台上的所有酒店
- 异常或边界情况：用户尝试操作自己没有权限处理的订单或酒店时，系统拒绝该操作并提示原因，不会因操作失败而改变订单状态（INT-02-L009, INT-02-L010）
- 验收方法：分别以三种角色登录，验证各角色可见功能和可操作数据范围是否符合权限定义；尝试越权操作验证是否被拒绝并提示原因
- 关联需求：REQ-002, REQ-003, REQ-004, REQ-020

### REQ-002 顾客匿名浏览与预订登录

- 类型：功能需求
- 来源：INT-01-L005, INT-01-L006
- 优先级：高
- 状态：已确认
- 需求描述：顾客无需登录即可查看酒店列表和房型信息；但在提交预订之前必须登录系统。
- 前置条件：顾客访问系统
- 正常结果：未登录顾客可浏览酒店和房型；点击预订时系统引导登录，登录后继续完成预订流程
- 异常或边界情况：无
- 验收方法：以未登录身份访问酒店页面确认可浏览；点击预订按钮确认是否跳转登录；登录后确认可继续完成预订
- 关联需求：REQ-001

### REQ-003 酒店信息管理

- 类型：功能需求
- 来源：INT-01-L008
- 优先级：高
- 状态：已确认
- 需求描述：酒店工作人员可以管理自己酒店的信息，包括酒店名称、城市、地址、联系方式和介绍等。
- 前置条件：酒店工作人员已登录
- 正常结果：酒店工作人员可查看和修改自己酒店的基本信息
- 异常或边界情况：酒店工作人员无法查看或修改其他酒店的信息（见REQ-001）
- 验收方法：以酒店工作人员身份登录，验证可修改和保存自己酒店的信息；尝试访问其他酒店信息确认无权操作
- 关联需求：REQ-001, REQ-022

### REQ-004 房型信息管理

- 类型：功能需求
- 来源：INT-01-L008
- 优先级：高
- 状态：已确认
- 需求描述：酒店工作人员可以管理自己酒店的房型信息，包括房型名称（如大床房、双床房、套房）、可入住人数和介绍。
- 前置条件：酒店工作人员已登录
- 正常结果：酒店工作人员可查看和修改自己酒店的房型信息
- 异常或边界情况：酒店工作人员无法管理其他酒店的房型（见REQ-001）
- 验收方法：以酒店工作人员身份登录，验证可创建、修改、查看自己酒店的房型信息；尝试访问其他酒店房型确认无权操作
- 关联需求：REQ-001, REQ-005

### REQ-005 房间数量与动态定价管理

- 类型：功能需求
- 来源：INT-01-L010
- 优先级：高
- 状态：已确认
- 需求描述：酒店工作人员可以为每个房型设置每天的可售房间数量和价格。不同日期（如周末、节假日）可以设置不同的价格和房间数量。
- 前置条件：酒店工作人员已登录，酒店已存在房型
- 正常结果：酒店工作人员可按日期设置各房型的房间数量和价格；顾客查询时可看到对应日期的价格
- 异常或边界情况：无
- 验收方法：以酒店工作人员身份为不同日期设置不同价格和房间数，确认保存成功；以顾客身份查询对应日期确认价格和房量正确显示
- 关联需求：REQ-004, REQ-007

### REQ-006 房型停售管理

- 类型：功能需求
- 来源：INT-01-L010, INT-02-L017, INT-02-L018
- 优先级：中
- 状态：已确认
- 需求描述：酒店工作人员可以将某个房型设置为停售状态。停售后顾客不能再预订该房型。停售不影响之前已生成的订单，已有订单继续有效，由酒店工作人员另行处理。
- 前置条件：酒店工作人员已登录，存在可停售的房型
- 正常结果：房型设为停售后，顾客查询时该房型不可预订；之前已生成的订单不受影响
- 异常或边界情况：停售后已有订单不会自动取消，需由酒店工作人员单独处理（INT-02-L017, INT-02-L018）
- 验收方法：设置房型停售后，以顾客身份确认无法预订该房型；检查已有订单确认未被取消
- 关联需求：REQ-004, REQ-007, REQ-016

### REQ-007 酒店查询

- 类型：功能需求
- 来源：INT-01-L012
- 优先级：高
- 状态：已确认
- 需求描述：顾客可以按城市、入住日期、退房日期、入住人数、房型和价格等条件查询酒店，支持多条件组合使用。查询结果需显示酒店和房型的基本信息、入住期间的价格，以及是否还有房可订。当没有符合条件的结果时，系统应提示未找到符合条件的酒店，不误导顾客认为还有房。
- 前置条件：顾客已访问酒店查询页面
- 正常结果：系统返回符合查询条件的酒店和房型列表，包含价格和有房信息；无结果时显示提示信息
- 异常或边界情况：无任何符合条件结果时，系统正常提示"未找到符合条件的酒店"，不会误导顾客
- 验收方法：使用不同查询条件组合进行测试，验证结果准确性和提示信息正确性
- 关联需求：REQ-005, REQ-008, REQ-009, REQ-021

### REQ-008 跨日预订库存校验

- 类型：功能需求
- 来源：INT-01-L013, INT-01-L014
- 优先级：高
- 状态：已确认
- 需求描述：顾客预订连续多晚时，入住日期到退房日期之间的每一晚都必须有可用房间才能预订成功。如果期间任何一天没有房或房型已停售，则不能预订该房型。
- 前置条件：顾客已选择酒店和房型，填写入住日期和退房日期
- 正常结果：入住至退房期间每晚均有房且房型未停售时，允许提交预订
- 异常或边界情况：入住至退房期间任一天无房或房型已停售时，系统拒绝预订并提示原因
- 验收方法：设置某房型仅在部分日期有房，尝试预订跨日订单验证系统是否正确拒绝
- 关联需求：REQ-007, REQ-009, REQ-010

### REQ-009 退房日期不计费规则

- 类型：功能需求
- 来源：INT-02-L013, INT-02-L014
- 优先级：高
- 状态：已确认
- 需求描述：退房日期当天不计入住宿晚数。例如顾客预订10月20日入住、10月22日退房，按两晚计算（10月20日、10月21日），只需保证10月20日和21日有房即可。
- 前置条件：顾客进行预订操作
- 正常结果：系统按入住日期到退房日期前一天计算住宿晚数，并据此校验库存和计算价格
- 异常或边界情况：无
- 验收方法：创建入住日期与退房日期相差多天的订单，验证住宿晚数计算和库存占用日期是否正确
- 关联需求：REQ-008, REQ-010

### REQ-010 预订提交与订单生成

- 类型：功能需求
- 来源：INT-01-L016, INT-02-L002
- 优先级：高
- 状态：已确认
- 需求描述：顾客选择酒店和房型，填写入住日期、退房日期和入住人数后提交预订。系统确认有房且房型可预订后生成订单，订单初始状态为"待确认"。
- 前置条件：顾客已登录，已选择酒店和房型，填写入住退房日期和入住人数
- 正常结果：系统校验通过后将订单状态设为"待确认"，订单生成成功
- 异常或边界情况：房间不足或房型不可预订时，订单不生成，系统提示原因
- 验收方法：以顾客身份提交预订，验证订单是否正确生成且状态为"待确认"；在无房情况下提交验证是否拒绝
- 关联需求：REQ-002, REQ-008, REQ-009, REQ-011, REQ-019

### REQ-011 订单状态管理

- 类型：功能需求
- 来源：INT-01-L018, INT-02-L002, INT-02-L007, INT-02-L008
- 优先级：高
- 状态：已确认
- 需求描述：订单有以下五种状态：待确认、已确认、已取消、已入住、已退房。状态流转规则如下：
  - 顾客提交预订后订单进入"待确认"状态
  - "待确认"可由酒店工作人员确认为"已确认"，或由顾客/酒店工作人员取消为"已取消"
  - "已确认"可由酒店工作人员办理入住变为"已入住"，或在入住前取消为"已取消"
  - "已入住"可由酒店工作人员办理退房变为"已退房"
  - "已取消"和"已退房"的订单不能再进行任何操作，不可恢复
  - 只有已确认的订单才能办理入住，只有已入住的订单才能办理退房
  - 办理入住和退房均由酒店工作人员操作，顾客不能自行将订单改为已确认、已入住或已退房
- 前置条件：订单已生成
- 正常结果：订单按规则在合法状态间流转，各操作由对应角色执行
- 异常或边界情况：尝试对不符合状态条件的订单执行操作时，系统拒绝并提示原因（INT-02-L008）；已取消或已退房的订单不可恢复（INT-01-L018）
- 验收方法：遍历所有状态流转路径，验证合法流转成功、非法流转被拒绝并提示原因
- 关联需求：REQ-010, REQ-012, REQ-013, REQ-018

### REQ-012 订单修改

- 类型：功能需求
- 来源：INT-01-L020, INT-02-L015, INT-02-L016
- 优先级：中
- 状态：已确认
- 需求描述：顾客可以修改订单的入住日期、退房日期和入住人数。修改后系统重新校验新日期的预订条件，如果新日期没有房则修改失败，原订单保持不变不被影响。
- 前置条件：订单处于可修改状态（入住前）
- 正常结果：修改后符合新预订条件时，订单信息更新成功
- 异常或边界情况：修改后新日期无房时，修改失败，原订单保持不变不丢失（INT-02-L015, INT-02-L016）
- 验收方法：修改订单日期为有房的日期验证修改成功；修改为无房的日期验证修改失败且原订单不变
- 关联需求：REQ-011, REQ-008

### REQ-013 订单取消

- 类型：功能需求
- 来源：INT-01-L020, INT-02-L006
- 优先级：高
- 状态：已确认（酒店工作人员取消的具体允许条件待确认）
- 需求描述：
  - 顾客可以在入住前取消自己的订单，取消成功后之前占用的房间重新释放可供其他顾客预订
  - 入住后不能取消订单
  - 酒店工作人员可以处理自己酒店的订单取消，取消时需记录处理理由并保留操作记录
  - 酒店工作人员允许取消的具体场景条件待进一步确认（INT-02-L006）
- 前置条件：订单处于可取消状态
- 正常结果：取消成功，订单状态变为"已取消"，占用房间释放
- 异常或边界情况：入住后的订单不能取消；酒店工作人员取消订单需记录理由（INT-02-L006）
- 验收方法：分别在入住前和入住后尝试取消订单验证权限控制；验证酒店工作人员取消时记录操作日志
- 关联需求：REQ-011, REQ-020

### REQ-014 订单价格锁定

- 类型：功能需求
- 来源：INT-01-L021, INT-01-L022
- 优先级：高
- 状态：已确认
- 需求描述：订单按照预订成功时的价格计算，酒店后续调整价格不影响已生成订单的价格。
- 前置条件：订单已生成
- 正常结果：已生成订单的价格保持不变，不受酒店后续调价影响
- 异常或边界情况：无
- 验收方法：预订后修改酒店价格，验证已有订单价格是否保持不变
- 关联需求：REQ-010

### REQ-015 并发预订与防重复提交控制

- 类型：功能需求
- 来源：INT-01-L023, INT-01-L024, INT-01-L025, INT-01-L026
- 优先级：高
- 状态：已确认
- 需求描述：
  - 最后一间房只能被一个顾客预订成功，不能出现超卖
  - 如果顾客页面显示有房但提交时房间已被他人订走，系统提示当前没有房，不生成订单
  - 同一顾客对完全相同的预订（相同房型、相同日期）重复提交时，系统提示已存在，不重复创建订单
  - 日期不同的预订可以正常提交
- 前置条件：顾客提交预订
- 正常结果：并发预订只成功一个；重复提交相同预订被识别并拒绝
- 异常或边界情况：页面显示有房但提交时无房时，提示"当前没有房"而非生成订单；重复点击提交不产生多个订单
- 验收方法：模拟并发提交相同预订验证只成功一个；快速重复提交验证不产生重复订单
- 关联需求：REQ-010

### REQ-016 酒店停业管理

- 类型：功能需求
- 来源：INT-01-L027, INT-01-L028
- 优先级：中
- 状态：已确认
- 需求描述：酒店停业后不再接受新预订。停业前已生成的订单保留不删除，由酒店工作人员单独处理。
- 前置条件：酒店工作人员操作酒店停业
- 正常结果：停业后该酒店不再接受新预订；已有订单保留
- 异常或边界情况：停业前订单不删除，由工作人员处理
- 验收方法：设置酒店停售后尝试预订验证是否拒绝；检查已有订单是否保留
- 关联需求：REQ-006, REQ-020

### REQ-017 待确认订单处理

- 类型：功能需求
- 来源：INT-02-L003, INT-02-L004
- 优先级：低
- 状态：已确认
- 需求描述：顾客提交预订后订单进入"待确认"状态，由酒店工作人员确认处理。目前暂不考虑自动取消待确认订单，但系统需要能标识哪些订单尚未确认。
- 前置条件：订单处于"待确认"状态
- 正常结果：系统展示待确认订单列表供酒店工作人员处理
- 异常或边界情况：暂不实现自动取消功能（INT-02-L003, INT-02-L004）
- 验收方法：验证系统能正确标识和展示待确认订单
- 关联需求：REQ-011

### REQ-018 操作失败处理

- 类型：功能需求
- 来源：INT-02-L009, INT-02-L010
- 优先级：高
- 状态：已确认
- 需求描述：当用户尝试操作没有权限的订单，或订单状态不符合操作条件时，系统应拒绝该操作并提示原因。操作失败时不能改变订单状态。相关重要操作应留下记录。
- 前置条件：用户尝试执行某项操作
- 正常结果：非法操作被拒绝，提示原因，订单状态不变
- 异常或边界情况：操作失败不导致订单状态被意外修改；重要操作即使失败也记录日志
- 验收方法：尝试各种非法操作（无权操作、状态不符合等），验证操作被拒绝且订单状态未变
- 关联需求：REQ-011, REQ-022

### REQ-019 待确认订单占用库存

- 类型：功能需求
- 来源：INT-02-L011, INT-02-L012
- 优先级：高
- 状态：已确认
- 需求描述：顾客提交预订后，即使订单处于"待确认"状态，对应房间也应算作已被占用（占用库存），防止同一房间被重复预订。
- 前置条件：顾客提交预订生成"待确认"订单
- 正常结果：待确认订单占用对应房型和日期的房间库存
- 异常或边界情况：无
- 验收方法：创建一个待确认订单后，以另一顾客身份查询同一房型同日期，验证是否显示无房
- 关联需求：REQ-010, REQ-017

### REQ-020 统计数据查看

- 类型：功能需求
- 来源：INT-01-L029, INT-01-L030
- 优先级：中
- 状态：已确认
- 需求描述：
  - 酒店工作人员可查看：每天的总房间数、已预订数量、剩余数量，以及一段时间内的订单数量和取消数量
  - 平台管理员可查看：平台上的酒店总数、正常营业的酒店数量，以及一段时间内的订单总数
- 前置条件：用户已登录且具有对应角色
- 正常结果：按角色展示对应统计数据
- 异常或边界情况：无
- 验收方法：分别以酒店工作人员和平台管理员身份登录，验证统计数据展示是否正确
- 关联需求：REQ-001

### REQ-021 操作日志

- 类型：功能需求
- 来源：INT-01-L031, INT-01-L032
- 优先级：中
- 状态：已确认
- 需求描述：系统需记录以下重要操作的日志：修改酒店信息、修改房型、调整房间数量和价格、创建或取消订单、确认订单、办理入住和退房、酒店停业等。日志应包含操作人、操作时间、操作内容和操作结果（是否成功），方便后续查问题。
- 前置条件：用户执行了需要记录的操作
- 正常结果：操作日志被正确记录，可查询
- 异常或边界情况：无
- 验收方法：执行各类需记录的操作，验证日志内容是否完整准确（操作人、时间、内容、结果）
- 关联需求：REQ-018

### REQ-022 查询响应时间

- 类型：非功能需求
- 来源：INT-01-L033, INT-01-L034, INT-02-L021, INT-02-L022, INT-02-L023
- 优先级：中
- 状态：待确认
- 需求描述：在正常使用情况下，酒店查询应在两秒内返回结果。具体测试条件和测试数量由开发团队根据实际查询场景制定验收测试方法。
- 前置条件：系统正常运行
- 正常结果：顾客执行酒店查询后两秒内看到查询结果
- 异常或边界情况：测试条件和具体验收标准待进一步制定（INT-01-L034, INT-02-L023）
- 验收方法：待确认（需根据实际查询场景制定测试条件和测试数量）
- 关联需求：REQ-007

### REQ-023 支付与退款约束

- 类型：约束
- 来源：INT-01-L028
- 优先级：低
- 状态：已确认
- 需求描述：系统暂不接入真实支付和退款功能。退款在线下处理，但订单取消等情况需在系统中记录。
- 前置条件：无
- 正常结果：订单取消等操作在系统内记录，不涉及真实支付流程
- 异常或边界情况：无
- 验收方法：验证系统不涉及真实支付流程；验证订单取消等操作有记录
- 关联需求：REQ-013
